# PostgreSQL Service 复杂方法步骤化注释设计

## 1. 目标

调整 PostgreSQL 学习模块中复杂 Service 方法的注释结构，使学习者在阅读实现细节前，
先看到完整的业务实现路线，再按照相同编号逐段阅读代码。

本次只调整注释，不改变方法签名、SQL、查询次数、事务边界、异常语义和返回结果。

## 2. 核心原则

复杂功能不能依靠零散行内注释拼凑出整体思路。每个复杂方法必须先回答两个问题：

1. 完成这个功能总共需要哪些步骤？
2. 下面每段代码分别在完成哪一步？

因此统一采用“方法开头完整步骤清单 + 代码阶段编号”的双层结构。

```java
public List<OrderDetailVO> getInnerOrderDetails(String orderNo) {
    /*
     * 实现步骤：
     * 1. 校验订单号并查询订单；
     * 2. 查询订单所属用户，关联不完整时返回空结果；
     * 3. 查询订单下的全部商品明细；
     * 4. 根据商品ID集合批量查询商品，避免 N+1；
     * 5. 按照 INNER JOIN 语义过滤并组装返回结果。
     */

    // 第1步：校验订单号并查询订单
    ...

    // 第2步：查询订单所属用户
    ...
}
```

## 3. 适用范围

不是所有方法都增加步骤清单。满足下面任一条件时，视为需要改造的复杂方法：

- 调用两个及以上 Mapper 或执行两次及以上数据库操作；
- 批量新增、批量更新或批量删除；
- 使用多个可选条件构造动态 Wrapper；
- 使用 Map、Set、分组、聚合、排序或多表 Java 组装；
- 包含多个业务校验和提前返回分支；
- 在一个事务中完成多个写入步骤；
- 为了保持 JOIN、聚合、空值或排序语义，需要分阶段处理数据。

简单 CRUD、单次 Mapper 转发、简单 getter/setter 组装不增加大段步骤注释，避免注释比代码更长。

## 4. MyBatis-Plus 改造范围

MyBatis-Plus 版本是本次重点，因为它需要通过多次单表查询和 Java 组装复现复杂 SQL 结果。

### 4.1 动态、分页和批量方法

- 动态用户、订单和商品查询：先校验请求，再构造条件，最后补充排序并执行查询。
- 用户和订单分页：先校验分页参数，再创建分页对象和条件，最后封装统一分页响应。
- 批量新增、批量更新状态和批量删除：先校验整个批次，再执行写操作并检查影响行数。
- 条件更新订单状态：先校验至少存在一个约束条件，再构造更新条件并执行更新。

### 4.2 JOIN 等价组装方法

六种 JOIN 案例全部采用步骤化注释：

- INNER JOIN：订单、用户、明细、商品的分阶段查询与完整关联过滤；
- LEFT JOIN：完整用户集合与身份证索引的左侧保留组装；
- RIGHT JOIN：完整用户集合、订单分组和空订单补位；
- FULL OUTER JOIN：两侧全集读取、匹配数据、孤儿明细和未售商品合并；
- CROSS JOIN：两侧数据读取、笛卡尔积生成和 limit 提前停止；
- LATERAL JOIN：订单分组选择最新记录，再与完整用户集合组装。

### 4.3 聚合和高级查询方法

对需要 Java 集合计算的统计、EXISTS/NOT EXISTS、HAVING、UNION ALL、状态映射、
排名、消费分层和商品销量统计方法增加步骤化注释。步骤清单必须写清楚：

- 哪些表被读取；
- 使用什么键建立 Map 或 Set；
- 如何保持 SQL 的过滤、空值、排序和聚合语义；
- 最终如何转换为 VO。

### 4.4 完整下单事务

完整下单方法保留现有详细业务说明，并统一成编号步骤：

1. 校验请求、用户和订单号；
2. 合并重复商品数量；
3. 批量加载并校验全部商品；
4. 计算服务端可信订单金额；
5. 写入订单头；
6. 按商品ID排序明细，统一并发加锁顺序；
7. 逐项写入明细并执行带库存条件的原子扣减；
8. 组装返回结果。

每个编号必须在实际代码的对应位置出现，异常发生时依赖既有事务配置整体回滚。

## 5. 普通 MyBatis 改造范围

普通 MyBatis 的 JOIN、聚合和高级查询通常由一条 XML SQL 完成，Service 只有参数校验和
一次 Mapper 调用，不强行增加多步骤清单。步骤化注释主要用于：

- 用户和订单分页的 COUNT、列表查询与分页封装；
- 批量新增、状态更新和批量删除；
- 枚举查询结果到扁平 VO 的转换；
- 完整下单事务。

复杂 SQL 的执行步骤继续写在 Mapper XML 中，Service 注释只描述其实际承担的业务编排，
避免把数据库内部逻辑重复抄到 Java 方法中。

## 6. 注释格式约束

- 总步骤使用阿拉伯数字：`1.`、`2.`、`3.`；
- 代码分段使用：`// 第1步：...`；
- 总步骤编号与代码分段编号必须一一对应，不得缺号或重复；
- 每一步描述业务意图和数据流，不只复述方法名；
- 在步骤中明确提前返回、空值、过滤或异常语义；
- 不为普通赋值、getter、setter 和显而易见的 Mapper 调用增加重复注释；
- 不在注释中承诺代码没有实现的性能、锁或事务效果；
- 原有解释 JOIN 语义、N+1、原子扣库存和死锁顺序的有效注释应保留并纳入对应步骤。

## 7. 验收标准

- Plus 版本全部多阶段复杂方法均先出现完整“实现步骤”清单；
- 每个总步骤都能在下面找到相同编号的代码分段；
- 普通 MyBatis 只在真正承担多阶段编排的方法中增加步骤清单；
- 简单 CRUD 保持简洁；
- 修改前后业务代码、SQL、事务注解和返回类型完全不变；
- 注释能先给出整体路线，再解释具体实现；
- 按用户既有要求不运行测试和构建，只进行静态格式与差异检查。
